# About the project

NeuroPilot is research software from the **Brain Networks** and **Neural Data
Science and Statistical Computing** groups at the Max Planck Institute for
Human Cognitive and Brain Sciences (*MPI CBS*) and the Center for Scalable Data
Analytics and Artificial Intelligence (*ScaDS.AI*), Leipzig, Germany. It runs
optimized TMS mapping experiments based on per-pulse electric fields, allows
for robot integration and ships a complete virtual twin to test and debug
workflows without hardware and subjects.

It is not a medical device. Real stimulation needs ethics approval, a trained
operator and the stimulator's own safety limits.

## What it is for

- **Reproducible coil placement.** The robot holds the coil on a tracked
  target instead of an operator holding it by hand.
- **A field, not a nominal target.** Every pulse is regressed against the
  E-field it actually delivered — from a precomputed library or from a SimNIBS
  solve for the realised pose.
- **A map while the session runs.** The per-element R² is shown on the cortical
  surface mesh as the pulses accumulate.
- **A twin for everything else.** Relay, neuronavigation and robot have virtual
  counterparts that speak the same topics, so a new user can learn the
  workflow and a developer can change it without hardware or a subject.

## How it came together

The suite grew out of a robot-assisted mapping pipeline and was consolidated
into one repository on **2026-11-10**. Before that it was four projects:

| Was | Is now |
|---|---|
| `cobot-pipeline-controller` | `neuropilot.controller` — GUI, state machine, analysis, online FEM |
| `relay_server_sim` | `neuropilot.sim_relay` — simulated Socket.IO relay |
| `tms-robot-sim2` | `neuropilot.sim_robot` — MuJoCo robot twin |
| `virtual_neuronavigation` | `neuropilot.sim_nav` — virtual InVesalius |

The merge was structural, not a rewrite: the modules kept their behaviour and
the relay topics stayed **byte-identical** to the production components. That
is the rule that makes the twin useful — the simulator can stand in for
InVesalius and the robot controller without either side knowing.

The production counterparts remain separate repositories:
[`tms-robot-control`](https://gitlab.gwdg.de/tms-localization/cobot/tms-robot-control)
for the robot controller and relay, and the group's
[InVesalius fork](https://gitlab.gwdg.de/tms-localization/cobot/invesalius-mpi) for
neuronavigation. NeuroPilot *uses* them in real mode; it does not replace them.

The controller, the virtual twin and the online E-field integration were
developed in Abdullah Yaseen's master's thesis (2026), supervised by Ole
Numssen and Prof. Dr. Barbara Wieczorek. The suite packages that work for
day-to-day use.

## How it is built

The design goals are deliberately boring:

- **One repository, one command.** `neuropilot sim` starts relay,
  neuronavigation, robot and controller in the right order, waits for each
  readiness probe and multiplexes one terminal's worth of logs.
- **One configuration source.** Shell > `.env` > lab profile > defaults, with
  the precedence documented and visible in the GUI.
- **No new runtime dependencies.** The supervisor is a few hundred lines of
  asyncio; the documentation site is generated by a standard-library script.
- **Upstream-friendly changes.** Additions to InVesalius and `tms-robot-control`
  are additive and unprefixed, so they can flow back.

Signal processing and the nine fit shapes come from
[`pynibs`](https://gitlab.gwdg.de/tms-localization/pynibs); the field modelling
from SimNIBS.

The parts that are not boring are tested: about 740 pytest tests, including
GUI tests, six-page visual baselines, property tests for the `.env` editor and
a relay-topic contract test. The documentation you are reading has its own
contract tests: every environment key, lab-profile key, relay topic and fit
function has to be documented, or CI fails.

## Contributing

Issues and merge requests are welcome on
[GitLab](https://gitlab.gwdg.de/tms-localization/papers/neuropilot/-/issues).
Before opening a merge request:

```bash
pytest -m "not gui" -q          # or scripts/run_tests.sh
python docs/site/build.py --check
```

If you change a setting, a relay topic or a fit function, add the matching row
to the docs — the contract tests will tell you if you forgot. Changes to code
that also exists upstream (InVesalius, `tms-robot-control`) must stay additive
and unprefixed; see [Add a component](extend/components.md).
